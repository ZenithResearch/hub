# Local-review actions on one Mac

The default bundle and installation remain `installation_only`. The opt-in v2 release uses the existing four fixed native payload roles and a separate `Process-Pilot` root, Runtime8192 and Service8191. It creates a private empty `exports` directory. Service stays default deny. Runtime uses `authority/config/runtime-receiver.json` and the existing `config/runtime-admission.json` FileAdmissionGate; its production `/ready` response is reported as returned, without relabeling it.

This source depends on the matching **new** Frank workflow CLI described below. The older installed-profile CLI does not implement these actions. The release profile, native and wheel pins must come from subsequent actual qualification; this change creates no placeholder release or live authority. The physical Mac is the target; no VM is required by this wiring.

Owner-selected files are fixed beneath the installation root:

- `config/pilot-setup-plan.json`: the Native setup owner's closed `castalia.wallet-local-review-setup.v1` document, with exact composition/source-manifest/native binary hashes and its finite permission window.
- `config/pilot-controller.json`: exactly `schema`=`hub.process-macos-pilot.v1`, `setup_plan_sha256` and `workflow_sha256`.
- `config/pilot-workflow.json`: the CLI owner's closed `frank.local-review.workflow.v1` document; actual pinned draft/compiled process and source artifacts, selected inputs, exact run and fixed `exports` directory. Its `profile_sha256` is the exact generated master hash.

These are owner-private0600 regular single-link files under private directories, with no symlink traversal. Initially `workflow_sha256` is null and the workflow file may be absent. This avoids a cycle: create-only Native setup generates the master and its keys; only then can the owner select the exact workflow/master hash. Execution rejects a missing workflow pin. The browser cannot choose paths, argv, a different process, permissions, a signer or a key.

Each action requires `--selection-sha256` over the exact controller document. The lightweight review also binds root inode/device, bundle digest, fixed public configuration hashes and a60s single-use plan. The existing Host/origin/CSRF checks and eight-plan cap remain.

1. `pilot-setup` calls only `native/castalia-wallet-local-review-setup create --plan config/pilot-setup-plan.json --plan-sha256 <selected pin>`. Existing or partial authority roots deny; no rekey/reset is offered. Native creates custody using its actual APIs. Hub never reads raw seeds. `authority/COMPLETE.json` means configured, not activated, and binds all seven emitted configuration files.
2. After the owner selects the post-setup workflow, `start` launches the existing Runtime with its actual receiver file and FileAdmissionGate, alongside default-deny Service. Frank is a bounded command, not a phantom listener/service.
3. `pilot-initialize` uses the existing Runtime admission operator/CAS to open new runs only in this isolated selected composition. An existing different policy denies rather than being replaced. The matching Frank CLI uploads actual declared artifacts, publishes the pinned process, registers the selected actor and creates the selected Run using its durable saved-command recovery.
4. `pilot-next` asks Runtime for actual eligible work and executes one canonical published operation. It does not infer readiness from step order.
5. `pilot-inspect` performs explicit authenticated reads and retains a dated safe summary of actual Run/output/receipt and journal facts. Periodic status reads that retained observation; it does not silently mint repeated native query sessions.
6. `pilot-resume` explicitly recovers exact retained work/commands; `pilot-renew` explicitly renews a retained result attestation without rerunning captured provider computation. Neither is a fresh-issue fallback after denial.
7. `pilot-export` writes only the actual committed `review_note` artifact as `<content_hash>.md` beneath the private fixed export root. Expected text is never treated as committed output.

The exact CLI invocation for the six workflow actions is installed Python `-I -B -m frank_executor.local_review_cli ACTION --config authority/config/frank-local-review.json --config-sha256 <COMPLETE master pin> --workflow config/pilot-workflow.json --workflow-sha256 <owner workflow pin>`. The CLI owner defines actual process/input schemas and validates them. `initialize,next,inspect,resume,renew,export` must be implemented and qualified before this release is usable. Old CLI forms remain owned by that component; Hub exposes no arbitrary effect-key/request-id browser arguments.

A successful mutation and its following inspection are separate outcomes. If the mutation succeeds but inspection is unavailable, Hub retains that success and reports inspection unavailable; it does not retry the mutation. An observation is dated and is never production readiness, speech-provider truth, useful-user-input acceptance, or external-effect permission. Fixture qualification remains explicitly a fixture. The actual user input must be selected honestly.

Before a pilot child launch, Hub persists `data/pilot-operation.json`. Successful, resolved cleanup removes only its matching operation. A hard-killed controller or forced/unresolved cleanup leaves a hold. The CLI separately owns `data/frank-local-review-cleanup.json`; any retained or malformed state blocks later native launches. CLI exit4 means cleanup unresolved, exit3 is an unknown business outcome only after cleanup resolves, and exit2 is denial only after cleanup resolves. Hub persists an unresolved state before forcing a child. Saved state is never future PID/PGID kill authority and is never silently erased on restart. Doctor, status and exact owned-service stop remain available; clearing a retained hold requires actual ownership/absence investigation, not blind PID signaling.

A pilot command has a90s deadline and2MiB spooled-output bound. On timeout/output bound Hub sends SIGINT and waits15s for the CLI's existing Wallet/result engines to drain, then records uncertainty before a forced kill and5s wait. A separate post-success inspection passes the fixed CLI `--wait-seconds 15` whole-action budget and has a30s wrapper deadline, reserving the remaining15s for cancellation/drain before the wrapper intervenes. Explicit manual inspection retains the CLI default60s action budget and90s wrapper deadline. The Node pilot/start deadline is240s, longer than the controller's inventory/policy/action/inspection/cleanup budget. Node's existing owned-process engine, error redaction and in-memory unresolved-cleanup quarantine are reused unchanged. Existing base commands retain their previous lifecycle.
