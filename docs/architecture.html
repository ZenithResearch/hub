Hub Architecture

A reference for anyone who has cloned or forked Hub and is spinning up their own instance. Covers every service, how data moves between them, and how to get it all running.

System Overview

Hub is a personal AI workspace that combines a Matrix homeserver, a durable message queue, an ephemeral event bus, an ingest layer, and an RSS feed poller — all wired together over a shared Docker network named agentnet.

Queue vs Event Bus — The Core Distinction

These two systems serve fundamentally different purposes. Confusing them is the most common architectural mistake to avoid when extending Hub.

Property Queue inbox/ · port 8081 Event Bus services/eventbus/ · port 8082
Model Pull-based. Workers claim jobs. durable Push-based. Subscribers receive events. ephemeral
Persistence SQLite — messages survive restarts and crashes. In-memory only — events lost if no subscriber is connected when published.
Who consumes One consumer (Frank) claims a message exclusively. Others never see it. Any number of subscribers see every matching event simultaneously (fan-out).
Lifecycle pending → processing → done / failed / DLQ
Messages are retried (max_retries), timed out (claim_timeout_s), dead-lettered.		 No lifecycle. Fire and forget. If nobody is subscribed, event is dropped.
What goes here Work items — things Frank must do: "respond to this message", "summarize this feed item". Facts that happened — "a job was enqueued", "a feed item arrived", "a Matrix message was received".
Primary use Frank session lifecycle, concierge requests, @-mention responses. Real-time UI updates (SwiftUI polls or subscribes SSE), inter-service notifications, monitoring.
Topic routing Named queues (e.g. workspace). Filtered by event_type on dequeue. Dot-notation topics with fnmatch wildcards: queue.job.*, feed.*, *.

How they interact

The Queue and Event Bus are peers — neither owns the other. But they cross-publish: when Ingest enqueues a job, it also publishes queue.job.enqueued to the event bus. Subscribers (SwiftUI, monitoring tools) learn a job arrived without touching the queue. Frank consumes the job from the queue without knowing anything about the event bus.

Queue — inbox/

A durable, SQLite-backed FIFO queue with retry logic, claim timeouts, and a dead-letter queue. Designed to be the single inbox Frank pulls from.

inbox/
  models.py    Message + QueueInfo dataclasses, MessageStatus constants
  store.py     QueueStore — all SQLite operations
  http.py      FastAPI app — enqueue / dequeue / ack / nack / peek / list
  service.py   QueueService — reaper loop (reclaims timed-out messages)
  config.py    QueueSettings via pydantic-settings
  main.py      Entry point — starts FastAPI + reaper

Message envelope

Every job in the queue carries this structure:

{
  "id":              "msg_abc123",
  "queue_name":     "workspace",
  "event_type":     "chat_message",       // what kind of trigger this is
  "source_type":    "matrix",             // where it came from: matrix | feed | http
  "sender":         "@alice:matrix.org",
  "message_body":   "Hey @hub can you summarise this thread?",
  "payload":        { "room_id": "!abc:localhost", "thread": [...] },
  "status":         "pending",             // pending | processing | done | failed | dlq
  "priority":       0,
  "retry_count":    0,
  "max_retries":    3,
  "claim_timeout_s": 300
}

HTTP API

POST /queues/{queue_name}/enqueue      // add a job
POST /queues/{queue_name}/dequeue      // claim next job (exclusive)
GET  /queues/{queue_name}/peek         // inspect without claiming
GET  /queues                           // list all queues with counts
POST /messages/{id}/ack                // mark done
POST /messages/{id}/nack               // return to queue or dead-letter
GET  /health

Retry and reaper

A background reaper runs every QUEUE_REAPER_INTERVAL_S seconds (default 30). Any message in processing state that has been claimed for longer than claim_timeout_s is automatically nacked and retried. After max_retries failures it moves to dlq.

Event Bus — services/eventbus/

An ephemeral, in-memory pub/sub broker exposed as Server-Sent Events (SSE). Any process can publish a named event; any client holding an open HTTP connection receives it in real time.

services/eventbus/
  broker.py   EventBroker — asyncio.Queue fan-out, fnmatch topic matching, module singleton
  http.py     FastAPI — POST /publish · GET /subscribe (SSE) · GET /health
  main.py     Entry point — uvicorn on port 8082

Publishing an event

POST http://eventbus:8082/publish
{
  "topic":   "queue.job.enqueued",
  "source":  "ingest",
  "payload": { "job_id": "msg_abc", "sender": "@alice:matrix.org" }
}

Subscribing via SSE

GET http://eventbus:8082/subscribe?topic=queue.job.*

# Wildcard examples
topic=*                  // everything
topic=queue.job.*        // all job events
topic=feed.*             // all feed events
topic=ingest.matrix.*    // all Matrix ingest events

Each event arrives as a standard SSE frame. The data field is JSON with id, topic, source, payload, and timestamp.

Topic conventions

queue.job.enqueued          // ingest pushed a job to the queue
feed.{feed_id}.item         // feeds service found a new RSS item
ingest.matrix.message       // Matrix message (no mention, no concierge)
frank.session.opened        // (future) Frank started handling a job
frank.session.closed        // (future) Frank finished

Slow consumer policy

Each subscriber gets a bounded asyncio queue (max 256 events). If a subscriber falls behind, events are silently dropped for that subscriber rather than blocking the broker. This keeps the broker non-blocking at the cost of delivery guarantees — acceptable for UI updates and monitoring, not suitable for critical work items (use the queue for those).

Matrix Homeserver — infra/matrix/

Each Hub instance runs its own Matrix Synapse homeserver. This is intentional: Hub is forkable. When you fork Hub, your instance gets its own homeserver with its own server_name. Federation (port 8448) is enabled by default so users on any Matrix homeserver — including other Hub instances — can join your rooms.

Federation design intent

The Hub codebase is a forkable template, not a single deployment. Each fork becomes an independent node. Matrix federation is the inter-node real-time layer — when two Hub instances federate, their rooms sync automatically over the Matrix protocol. No custom bridge or relay is needed.

For federation to work your homeserver needs a public domain name and port 8448 reachable from the internet. Local development on localhost works for intra-hub testing but federation with external servers requires a public host.

Ingest Service — services/ingest/

A Matrix bot client (@hub:localhost) that connects to your Synapse homeserver, listens for room events, and routes them into the rest of the system.

services/ingest/
  matrix_client.py  HubBotClient — matrix-nio AsyncClient, event routing logic
  normalizer.py     normalize_mention() + normalize_concierge() → QueuePayload
  config.py         IngestSettings — MATRIX_HOMESERVER, MATRIX_USER, CONCIERGE_ROOM_IDS, etc.
  main.py          Entry point — asyncio.run(HubBotClient.start())

Routing logic

For every message the bot sees in any joined room:

room is in CONCIERGE_ROOM_IDS
→
enqueue (last message only, no thread)
@hub mentioned in message
→
fetch last 20 messages as thread
→
enqueue (with thread context)
all other messages
→
event bus only
ingest.matrix.message

After enqueueing, the bot also publishes queue.job.enqueued to the event bus.

Startup sequence

On startup the bot does an initial sync with timeout=0 to drain the backlog of messages that arrived while it was offline — without processing them. This prevents replaying old messages on every restart. Then it calls sync_forever(timeout=30_000) to receive live events.

Feeds Service — services/feeds/

Polls RSS and Atom feeds on configurable intervals. Deduplicates items using a SQLite seen-GUIDs table. Publishes new items to the event bus and optionally enqueues them for Frank if keywords match.

services/feeds/
  main.py     Entry point — reads FEEDS_CONFIG JSON, starts one poll loop per feed
  fetcher.py   FeedFetcher — feedparser + SQLite dedup at /data/feeds.db
  models.py    FeedConfig + FeedItem dataclasses

Feed configuration

Set the FEEDS_CONFIG environment variable to a JSON array. If empty or unset, the service starts idle and waits.

    "id": "hn",

]'

Getting Started — Spinning Up a Fresh Instance

These steps are written for someone who has just cloned or forked Hub and wants to run the full stack locally.

Prerequisites

  • Docker Desktop (or Docker Engine + Compose v2)
  • Python 3.11+ (only needed if running services outside Docker)
  • The envsubst CLI (part of gettext — brew install gettext on Mac)

Step 1 — Create the shared network

All services join a Docker network called agentnet. It must exist before any compose stack starts. Create it once: 

docker network create agentnet

Step 2 — Configure environment variables

Copy the example env file and fill in the required secrets:

cp .env.example .env    # or create .env from scratch

Minimum required values in .env:

# Matrix / Synapse
MATRIX_SERVER_NAME=localhost           # change to your domain for federation
MATRIX_DB_PASSWORD=<random-hex>
MATRIX_REGISTRATION_SECRET=<random-hex>
MATRIX_MACAROON_SECRET=<random-hex>
MATRIX_FORM_SECRET=<random-hex>
MATRIX_DB_USER=synapse
MATRIX_DB_NAME=synapse
MATRIX_DB_HOST=matrix-db
MATRIX_DB_PORT=5432
MATRIX_HTTP_PORT=8008
MATRIX_HTTPS_PORT=8448
MATRIX_USER=@hub:localhost
MATRIX_PASSWORD=<set this after first run>

Generate random secrets with:

openssl rand -hex 32

Step 3 — Render the Synapse config

The config template uses $VAR substitution. Render it to homeserver-local.yaml (gitignored) before starting Synapse: 

cd infra/matrix
set -a && source ../../.env && set +a
envsubst < config/homeserver.yaml > config/homeserver-local.yaml

Step 4 — Start Matrix

cd infra/matrix
docker compose up -d

Wait for the healthcheck to pass (~30s). Verify Synapse is up: 

curl http://localhost:8008/health    # should return {}

Step 5 — Create the hub bot user

The ingest service logs in as @hub:localhost. Create this user via the admin API (requires the registration secret from your .env): 

# Create an admin user first (one-time, use your registration secret)
curl -X POST http://localhost:8008/_matrix/client/v3/register \
  -H "Content-Type: application/json" \
  -d '{
    "username": "admin",
    "password": "<your-admin-password>",
    "auth": {"type": "m.login.registration_token", "token": "<MATRIX_REGISTRATION_SECRET>"}
  }'

# Get an admin access token
curl -X POST http://localhost:8008/_matrix/client/v3/login \
  -d '{"type":"m.login.password","user":"admin","password":"<your-admin-password>"}'

# Create the hub bot user via admin API
curl -X PUT http://localhost:8008/_synapse/admin/v2/users/@hub:localhost \
  -H "Authorization: Bearer <admin-access-token>" \
  -H "Content-Type: application/json" \
  -d '{"password": "<MATRIX_PASSWORD>", "admin": false}'

Set MATRIX_PASSWORD in your .env to whatever password you used above.

Step 6 — Start the hub services

cd /path/to/hub
docker compose up -d

This starts: queue, eventbus, ingest, feeds, gateway-http, runtime-grpc, tool-sandbox, kb-indexer, qdrant.

Verify everything is up:

curl http://localhost:8081/health    # queue
curl http://localhost:8082/health    # event bus
curl http://localhost:8080/health    # gateway

Step 7 — Configure feeds (optional)

Add feeds by setting FEEDS_CONFIG in your .env before starting, or by updating the environment in docker-compose.yml and restarting the feeds service: 

docker compose restart feeds

Step 8 — Connect a Matrix client

Point any Matrix client (Element, FluffyChat, etc.) at http://localhost:8008 to create rooms and send messages. The ingest bot will automatically pick up @-mentions and concierge room messages.
